## [2026-11-24 11:08] Change #13: Open JAV library playback from the known file path
- **Purpose**: Selection from the JAV library froze on entry and made seekbar drags much worse, while opening the same file from a folder played normally. The user's evidence pointed at the JAV entry path, not the seekbar.
- **Approach**: JAV library items come from `LibraryIndexRepository.toVideo()`, which produces a `content://media/...` URI whenever the MediaStore id is known. Folder/file launches come from `MediaFileRepository`, which produces `file://` URIs. The content path makes PlayerActivity call `getFileName` (MediaStore query), `getPlayableUri`/`parsePathFromIntent` (`openContentFd`: fd + `findRealPath` + MediaStore) and the subtitle autoload path on the main thread; the JAV entry also passes `media_code`, so `SubtitleOps.loadJavSubtitles` added all matching JAV subtitles with `MPVLib.command("sub-add")` from `Dispatchers.Main`. Opening the file directly skipped the content resolver and the code-forced subtitle add.
- **Proposal**: Carry `display_name` and `file_path` in the internal Video intent, prefer them in PlayerActivity, move content-URI fallback resolution and subtitle adds off the main thread, and fast-path `file://` in `openContentFd`.
- **Decision**: `MediaUtils.playFile(Video)` now sends `display_name` and `file_path`; `PlayerActivity.getFileName` reads the name extra, `parsePathFromIntent` returns a readable `file_path` first, playback start and onNewIntent resolution run on IO, autoload passes a content URI through instead of resolving it, and playlist path resolution runs on IO. `SubtitleOps` adds both JAV and local sidecar subtitles on IO. `openContentFd` returns the path immediately for `file://`.
- **Files**: `utils/media/MediaUtils.kt`, `ui/player/PlayerActivity.kt`, `ui/player/PlayerUtils.kt`, `utils/media/SubtitleOps.kt`, `UNRELEASED.md`.
- **Risks**: A content URI without a readable `file_path` still uses the resolver, now on IO; if the path is stale or unreadable, playback falls back to the old content path. Delaying `player.playFile` by one IO resolution may shift the first frame slightly. Subtitle tracks are still added in the same order, now off main; a heavy bitmap subtitle can still slow mpv's decoder. No layout or seek mode changed.
- **Verification**: PR #8 Unit Tests run 45317498188 passed in 3m1s and CI Build run 45317498253 passed in 3m49s on `fbcbebd`. The universal APK is 101,291,403 bytes, SHA-256 `45EA8461354E73268A96AC4D899AA8F7504339636DF3D04FF8E8A5ACE7E5BE6B`, has 1,287 ZIP entries, five dex files, and an APK signing block; it is copied to `dist-apk/app-standard-release.apk`. Device comparison of JAV entry vs folder playback and 20-30 seekbar drags is still required; no adb is available locally.
- **Lesson**: The same file behaves differently depending on which repository built its `Video`: the library index emits `content://` when a MediaStore id exists, while folder browsing emits `file://`. Compare those constructors before blaming the seek pipeline; the content resolver work and code-forced subtitle add were both on the main thread.

## [2026-11-23 21:04] Change #12: Keep mpv property polling and MediaSession updates off the main thread
- **Purpose**: Dragging the seekbar several times could freeze the player. Seeking holds mpv's property/core lock, while the app polled blocking `MPVLib.getPropertyDouble("time-pos")` from the main thread every 42 ms and read `time-pos` again inside the MediaPlaybackService observer. Repeated drags turned that contention into an ANR-like freeze.
- **Approach**: `viewModelScope` defaults to `Dispatchers.Main.immediate`; the 42 ms precise-position loop, duration/volume/hr-seek collectors, the 250 ms auxiliary poller, and the intro poller all reached mpv from Main. The service also read `time-pos` from mpv's own event callback and built notifications on that thread. Options considered: switch every poll to `MPVLib.propDouble` flows (changes update cadence and is unverified for 24 FPS smoothness) or move the blocking reads to a dedicated thread while keeping the UI state on Main. Chose the dedicated thread because it preserves the existing cadence and keeps the fix local.
- **Proposal**: Use one daemon single-thread dispatcher for mpv property reads; keep UI-owned sets and StateFlow writes on Main; use the observer's `time-pos` value in the service and move MediaSession/notification work to a Default scope. Also stop resuming after a seek that was superseded by a newer drag.
- **Decision**: Added `mpvPollDispatcher` backed by `mpv-property-poll`, moved the precise-position/duration/volume/hr-seek collectors to it, wrapped the intro and auxiliary mpv reads in `withContext`, and made `updateShaderPeek` take the height read in the same snapshot. The service now stores `lastKnownPositionMs`, schedules `updateMediaSession` on `serviceScope`, and no longer calls `getPropertyDouble("time-pos")` from the observer. `seekToAndResume` checks `dispatchAbsoluteSeek` before requesting audio focus or unpausing. The executor is shut down in `onCleared`.
- **Files**: `ui/player/PlayerViewModel.kt`, `ui/player/MediaPlaybackService.kt`, `UNRELEASED.md`.
- **Risks**: While a blocking mpv read is slow, the seekbar can hold its last value for that interval, but the UI thread stays responsive. MediaSession metadata/notification updates are now asynchronous and can lag by up to one second; the notification still starts with the intent-provided media info. No seek behavior or layout changed.
- **Verification**: PR #8 Unit Tests run 45180555217 passed in 3m23s and CI Build run 45180555107 passed in 6m20s on `e9d5e83`. The universal APK is 101,289,859 bytes, SHA-256 `50EABBBD4B5D0852A299BCFB611FC120F00C1140B903DBF29C1BCC77A45B79E1`, has 1,287 ZIP entries, five dex files, and an APK signing block; it is copied to `dist-apk/app-standard-release.apk`. `git diff --check` is clean. No local Gradle or adb is available, so the 20-30-drag device repro and `lastanr` check remain pending.
- **Lesson**: `viewModelScope` is Main.immediate, not IO. A 24 FPS property poll is a 24 FPS blocking JNI call on the UI thread; move the read, not just the state update. The AAR's `MPVLib.propInt/propBoolean` flows already map on `MPVLib.scope` (`Dispatchers.IO`), so the explicit poll loops were the main-thread offenders; this was confirmed by inspecting the AAR bytecode before changing code.

## [2026-11-18 20:05] Change #10: Pin CI and local side-load signing so APKs upgrade in place
- **Purpose**: Every CI build signed the release APK with a freshly generated debug keystore, so installing a newer artifact over an existing one failed with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`. The only workaround was to uninstall, which deleted the Room database, downloaded JAV covers, and Chinese subtitles from app-private storage.
- **Approach**: Android requires the same signing certificate for an in-place update; no adb or installer flag bypasses that check. Options considered: (a) reuse the repository `SIGNING_KEYSTORE` secret - unavailable for this fork; (b) cache `~/.android/debug.keystore` in GitHub Actions - evicted and not shared with local builds; (c) commit a dedicated public side-load keystore used only by `build.yml` and local release builds, while `release.yml`/`preview.yml` keep secret-based signing for published artifacts. Chose (c) because the fork has no release secrets and the key only protects direct APK upgrades, not store distribution.
- **Proposal**: Add a `sideload` signing config backed by `keystore/sideload.p12`, opt in with `-PsideloadSigning`, and switch `build.yml` from `-PciDebugSigning` to it. Keep `ciDebugSigning` as a fallback for other branches.
- **Decision**: Added the fixed `sideload` signing config and switched the CI build to `-PsideloadSigning`. Existing installs signed by the old random debug key cannot be upgraded in place; this change only stops the problem from recurring.
- **Files**: `keystore/sideload.p12`, `app/build.gradle.kts`, `.github/workflows/build.yml`, `DEVLOG.md`.
- **Risks**: The side-load private key is public in the repository. Anyone can sign an APK with the same package name, so only install APKs downloaded from this fork's Actions run. Published GitHub releases still use the repository secret, so switching between a published release and a CI artifact still requires one uninstall. `release.yml` and `preview.yml` are untouched.
- **Verification**: `CI Build` run 44302689575 passed in 5m20s with `-PsideloadSigning`, and `Unit Tests` run 44302689571 passed in 2m16s. The first attempt failed with `No key with alias 'mpvium'` because the Windows PKCS12 export dropped the friendlyName; re-exporting with OpenSSL `-name mpvium` fixed it, which also proves AGP reads the alias. `git diff --check` clean. Installing over the previously CI-signed APK still needs one uninstall because that APK used the old random debug key; the in-place check applies to the next build.
- **Lesson**: PKCS12 keystores need an explicit friendlyName. `Export-PfxCertificate` did not persist it even after setting `FriendlyName` on the certificate object; verify with `openssl pkcs12 -in ... -nodes` before committing a keystore.
